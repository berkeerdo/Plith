# R7 parity research: WPF 0.3.1 vs Rust (2026-11-24)

Read-only research. Sources: `src/Plith/**`, `src/Plith.Installer/**`, `docs/wpf/`, `docs/ROADMAP.md`,
`docs/STATUS.md`, `docs/specs/2026-11-14-rust-rewrite-design.md`, `docs/specs/2026-11-20-r7-settings-window-design.md`,

repo-wide grep over `crates/` found nothing.

Important framing: the Rust design deliberately dropped or changed some WPF features (design spec section 3, ADR 0007,
settings spec section 2 non-goals). Those rows say "dropped by design" and need only a parity-doc note, not code.

## 2. Tray

### WPF (`src/Plith/Services/TrayIconHost.cs`)
- Library: Hardcodet.NotifyIcon.Wpf 2.0.1 (`Plith.csproj:101`; `publish/Hardcodet.NotifyIcon.Wpf.dll`).
- Icon: `Resources/icons/plith.ico` loaded from the pack URI, fallback `SystemIcons.Application` (`:150-166`).
- Tooltip: the single string `Plith` (`:42-46`).
- Context menu (`:48-90`), in order:
  1. `Settings…` opens or activates the one settings window.
  2. `Create diagnostic bundle` (only if a log exists): zip to Desktop with the log and an environment snapshot, then
     Explorer `/select`. Runs off the UI thread because brightness DDC reads cost 56 ms per monitor.
  3. separator
  4. `Exit`: logs "Exit clicked", posts `Shutdown` at Background priority (calling it inline from the click wedged the
     dispatcher; measured 2.6 s stall on 2026-10-12).
- Double click on the icon opens Settings (`:93`). No single-click action, no balloon notifications, no status badge.
- `Dispose` removes the icon at exit.

### Rust today
- No tray. `grep Shell_NotifyIcon|NOTIFYICONDATA` over `crates/` returns nothing. The only hits for "tray" are the
  `Shell_TrayWnd` class name in a topmost test (`plith/src/app/wire/tests.rs:25`) and the doc comment in
  `plith-shell/Cargo.toml:3` and `plith-shell/src/lib.rs:1`, which already promises "OLE drag and drop and the tray".
  Nothing implements it.
- ADR 0002 lists "tray" among `plith.exe` duties; the settings spec (2026-11-20, section 2) deferred it to later R7.
- Building blocks present: a message-only/UI-thread loop, `UiWaker`/`ShapePoster` (WM_APP posting), `QuitHandle`
  (`plith-shell`, used in `app/wire.rs:116`), a settings window that opens from the island (gear) and can be reopened
  ("a second open restores and focuses", spec section 5), and the log.
- Suggested tray scope for parity: icon + tooltip `Plith`; menu `Ayarlar` (open settings), `Tanı paketi` (diagnostic zip,
  optional), separator, `Çık` (QuitHandle); left double click = settings; handle `TaskbarCreated` to re-add after
  Explorer restart (WPF's NotifyIcon library did this for free; a raw `Shell_NotifyIconW` implementation must do it).
  Menu text from the eight-language table. No wakes at rest (tray is message-driven).

## 3. Installer and release

### How WPF 0.3.x shipped
- Installer project `src/Plith.Installer` (WPF, .NET, `app.manifest:11` `requireAdministrator`). Pages: Welcome (with
  "Launch at Windows login" checkbox, `WelcomePage.xaml:102`), Progress, Finish (launches Plith through `explorer.exe`
  so the app runs un-elevated, `FinishPage.xaml.cs:56-63`), Error, UninstallConfirm, UninstallFinish.
- Build: `scripts/build-release.ps1` (admin): shared-XAML check, contrast check, both test suites, `dotnet publish`
  of the installer as a single-file self-contained self-extracting exe (about 40 MB), renamed to
  `release/Plith-Setup-<version>.exe`, signed with `signtool` using cert `CN=Plith Self-Signed` from `CurrentUser\My`
  (SHA256, DigiCert timestamp). The installer embeds a zip of the published app, signed at build time by
  `scripts/sign-plith.ps1` (called from `Plith.Installer.csproj` target `PublishPlithAndEmbed`). Current artifact:
  `release/Plith-Setup-0.3.3.exe`. `scripts/manual-install.ps1` and `one-shot-install.ps1` are Norton-era
  workarounds, `scripts/*msaccount*` are unrelated one-off cleanups.
- Install flow (`InstallOrchestrator.cs:36-95`), per-machine, needs admin:
  1. `CertService.InstallTrust()` puts the embedded public cert into `LocalMachine\Root` and `LocalMachine\TrustedPublisher`
     (both required for the UIAccess chain; `CertService.cs:8-40`).
  2. Extract bundle to a stage dir.
  3. Copy to `C:\Program Files\Plith` (`InstallDir`, line 11), after Restart Manager and a multi-round kill (with
     `SeDebugPrivilege`) of a running UIAccess Plith. Uninstaller copy to `Program Files\Plith\Setup\Plith-Uninstaller.exe`.
  4. Start Menu shortcut, `HKLM\...\Uninstall\Plith` (DisplayName, DisplayVersion, Publisher `Plith Self-Signed`,
     UninstallString = `Plith-Uninstaller.exe --uninstall`), auto-start Run value if the box was ticked.
- Uninstall (`:360-410`): kill Plith, remove Run value, uninstall entry, Start Menu shortcut, then a spawned `cmd`
  deletes `Program Files\Plith` after 8 s (self-delete). The self-signed certificate stays in the trust stores
  (README line 97-100 says so). User data in `%LOCALAPPDATA%\Plith` is left.
- In WPF the whole app ran as UIAccess High integrity (`app.release.manifest:12`), which is why the shelf needed
  `Plith.DropCatcher` (ADR 0002 context).
- Update: none. `UpdateCheckService` polls `api.github.com/repos/berkeerdo/Plith/releases/latest` and downloads the
  `Plith-Setup-*.exe` asset from Settings > Updates on demand. No throttled background check.
- Signing reality: self-signed `CN=Plith Self-Signed`, SmartScreen warns on first run. Real certificate (SignPath OSS or
  paid) and MSIX are open items (`docs/wpf/ROADMAP.md:156-166`, README line 230, design spec lines 34 and 166-167).

### Rust OSD helper today (dev flow, not a product install)
- `scripts/build-osd.ps1`: finds `CN=Plith Self-Signed` with a private key in `CurrentUser\My`, builds
  `plith-osd` with `PLITH_OSD_UIACCESS=1` through `heavy-run.mjs`, signs with signtool (SHA256 + DigiCert timestamp),
  verifies `Valid`, prints SHA-256 and thumbprint. Never creates or imports a cert.
- `scripts/install-osd.ps1`: under `sudo`, `-Yes -Sha256 <hex>`. Pins thumbprint `144A7919A1FC941FDC3A9443C1DBAA7AE002AC0F`
  (CN=Plith Self-Signed, valid to 2031-05-30; a public thumbprint, not a secret) and the exact hash. Copies to
  `C:\Program Files\Plith\osd\plith-osd.exe` via `.new` temp, asserts that only SYSTEM, Administrators and TrustedInstaller
  can write the install (Assert-AdminOnly on `Program Files\Plith`, `osd`, exe), stops a running helper by exact path first.
  `-CheckAcl` read-only check; `-Uninstall -Yes` stops the helper, deletes the exe and the empty `osd` dir.
- It does NOT install the certificate into `LocalMachine\Root`/`TrustedPublisher` (grep: no trust-store code). On this PC
  the trust was set up earlier by the WPF installer. A clean machine would get "signature not trusted" and no UIAccess.
- The client side: `plith-ipc/src/launch.rs:24` hardcodes `INSTALLED_HELPER = C:\Program Files\Plith\osd\plith-osd.exe`;
  start uses `ShellExecuteExW` because plain `CreateProcess` fails on a `uiAccess` exe (`launch.rs:95-122`). A dev
  `plith.exe` trusts only that installed helper (STATUS open risk). The pipe client verifies the server's user and
  integrity level.
- `plith-osd/build.rs` embeds `plith-osd.manifest` with `uiAccess='false'` by default and `'true'` when
  `PLITH_OSD_UIACCESS` is set.
- Why the secure location: Windows grants UIAccess only to an exe that is signed by a cert chaining to a trusted root and
  lives in a secure folder (Program Files, System32); ADR 0002 and 0009 confirm helper runs at High integrity,
  `CreateWindowInBand(ZBID_UIACCESS)` works only then.
- `plith.exe` itself: `asInvoker`, medium integrity, no installer, run from `target\release` or `dist\`. `plith-osd` is
  not signed in CI. Untracked: `crates/plith` has no manifest, no icon, no version resource.

### What a Rust installer must do
1. Elevation: one elevated install step (Program Files + HKLM). `plith.exe` is never launched elevated, and the Finish
   page starts it through `explorer.exe` (as WPF did) so it stays medium.
2. Layout: `C:\Program Files\Plith\plith.exe` and `C:\Program Files\Plith\osd\plith-osd.exe` (path is hardcoded in
   `launch.rs:24`; keep or move both together and change the const). `plith.exe` can live in Program Files too (per-machine,
   same folder ACL as the helper) or per-user (`%LOCALAPPDATA%\Programs\Plith`); only the helper needs the secure path.
   Recommended: one per-machine root, helper in `osd\`, folder ACL admin-only (reuse `Assert-AdminOnly`).
3. Trust: put the public cert into `LocalMachine\Root` and `TrustedPublisher` (WPF `CertService` logic) before the helper
   is started, else no UIAccess. Weigh this: installing a self-signed root machine-wide is the main user-facing smell; a
   real code-signing cert (SignPath OSS / OV / Azure Trusted Signing) removes it. Does a real cert chain to a public root
   without the Root store step? Yes, for UIAccess a publicly trusted chain is enough.
4. Both exes signed (plith.exe for SmartScreen, helper for UIAccess) with SHA256 and timestamp; the hash pin in
   `install-osd.ps1` becomes a build artifact check (the installer ships the exact signed bytes).
5. Kill before replace: stop `plith.exe` (WM_CLOSE to `Plith.Notch`, then Restart Manager) and `plith-osd.exe` by exact
   path (copy `Stop-InstalledOsd`); WPF needed SeDebugPrivilege for a UIAccess target. The helper is High integrity, so an
   elevated installer can stop it, a medium `plith.exe` cannot kill it (hence the helper should also exit when its pipe
   client goes away; check `plith-osd/src/watch.rs`).
6. Start with Windows: HKCU `...\CurrentVersion\Run` value `Plith` pointing at `plith.exe` (medium, per user, same as WPF
   `AutoStartService`), set from an installer checkbox and a settings row. The helper is not in Run: `plith.exe`'s
   supervisor starts it (`plith/src/osd/supervisor.rs`).
7. Start Menu shortcut, `HKLM\...\Uninstall\Plith` (DisplayName, DisplayVersion read from the exe's VERSIONINFO,
   Publisher, DisplayIcon, UninstallString, EstimatedSize, InstallLocation), `plith.ico` embedded.
8. Uninstall: stop `plith.exe` and `plith-osd.exe`, delete both and the `osd` folder, Run value, Start Menu shortcut,
   uninstall key; ask whether to keep `%LOCALAPPDATA%\Plith` (settings, shelf, plays). Optionally offer to remove the
   cert from the trust stores (WPF left it).
9. Upgrade over WPF 0.3.x: the old per-machine install at the same `C:\Program Files\Plith` and the same Uninstall key
   `Plith`. The Rust installer must remove `Plith.exe`, `Plith.dll`, the .NET runtime files and `Hardcodet.*` etc. (WPF's
   MirrorCopy deleted target-only files; do the same, except `osd\`) and the old DropCatcher if present, and carry the
   Run value over (same name `Plith`, new path).
10. Technology choices (not decided in docs): hand-written Rust installer, Inno Setup (a script, handles ACL, Run key,
    uninstall, Restart Manager, code-signed), or WiX/MSI. Inno Setup is the smallest path and signs both the installer and
    uninstaller; custom actions are Pascal. A WPF installer is explicitly not wanted (that is being removed).
11. Pre-release gate: the unmeasured "standard (non-admin) user" case (STATUS open risk): the medium notch trusts only a
    server strictly above its own integrity level, so on a standard user the helper's level may be equal and the client
    fails closed. Must be measured on a non-admin account before the installer ships.
12. Release pipeline: `scripts/build-release.ps1` is WPF only; a Rust equivalent builds with `heavy-run.mjs`
    (`cargo build --release --workspace`), builds the helper with `PLITH_OSD_UIACCESS=1`, signs, packs, signs the
    installer, writes `release/Plith-Setup-<version>.exe` (name unchanged so the old GitHub asset prefix still matches
    `UpdateCheckService`, and the WPF 0.3.x "Check for updates" button then sees the Rust release as an update).
    `scripts/check-publish-shape.ps1` and `check-win32-flags.ps1` need a read (WPF-specific?).

### Code signing certificate notes (no secrets)
- Only a self-signed cert `CN=Plith Self-Signed` exists, in `CurrentUser\My` of the dev machine, thumbprint pinned in
  `scripts/install-osd.ps1:25`, expiry 2031-05-30. The installer embeds only the public part
  (`Plith.Installer/Resources`, via `sign-plith.ps1 -CertOutput`). Private key is never in the repo.
- A real certificate is an open ROADMAP item since 0.1.x (SignPath OSS application, or paid). The design spec keeps it as a
  ROADMAP item and calls auto-update blocked on it.
- `sign-plith.ps1` still contains `New-SelfSignedCertificate` (creates a 5-year cert if none) while `build-osd.ps1` says
  "never creates one". Pick one policy before the Rust release.

## 4. Gaps ranked

### Blocks "WPF removed" (must do in R7)
1. Installer and uninstaller for the Rust app (item 3), including helper in `Program Files\Plith\osd`, trust store step,
   per-machine layout, upgrade over a WPF install, uninstall that stops both exes. Without it WPF cannot be removed because
   the only way to install Plith today is the WPF installer.
2. Tray icon with Settings and Exit (Section 2) and an exe icon (`plith.ico` embedded via `build.rs`/`winres`-style
   resource). Without a tray, a start-with-Windows app cannot be exited or configured except by a click on the gear.
3. Start with Windows: Run key writer, a Genel row `Windows ile başlat`, the installer checkbox.
4. Clean exit path and version resource (so installer and Add/Remove Programs show the version; `0.1.0` in `Cargo.toml`
   versus WPF 0.3.3 shipped: decide the number, probably 0.4.0 or 1.0.0, so the upgrade is a higher version for
   `UpdateCheckService` compare).
5. Standard-user integrity measurement for the helper (STATUS open risk), plus the console run over a game (osd Task 9)
   and the remaining "owed on screen" items in STATUS (relayout Task 5, settings console session, shelf real drag,
   weather `OKUMA`). Parity check cannot be called done on RDP alone.
6. Settings migration from WPF `config.ini`: at least start-with-Windows state, weather city, theme (Dark maps to Gece),
   and endpoint pin if pinning is kept.
7. Decisions to write as an ADR or a parity doc: which WPF settings are dropped by design (position, presentation, opacity,
   thresholds, compact mode, accent picker, hover keep-alive, fullscreen-video hide). The parity check needs a signed-off
   list from Berke, since the roadmap says "parity check against WPF 0.3.1".
8. Endpoint pinning and brightness hotkeys, if Berke keeps them: both shipped in 0.3.1 and the settings spec promised
   pin migration. Hotkeys are the only brightness trigger on a desktop with an external monitor. Either build or list as
   dropped by design.
9. The R4b media output picker: shipped in WPF 0.2.0, parked in Rust on an RDP probe failure. Either finish or drop
   with Berke's yes.
10. A second cleanup commit: delete `src/`, `tests/Plith*.Tests`, `Plith.slnx`, `publish/`, `release/` WPF artifacts,
