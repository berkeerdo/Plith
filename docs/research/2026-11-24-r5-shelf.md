### RegisterDragDrop on this window: does it work?
- No known blocker, and nothing in the repo contradicts it, but it is UNVERIFIED on this window. Reasons it should work: OLE finds the target with `WindowFromPoint`-style hit testing on every mouse move of the drag loop and reads the `OleDropTargetInterface` window property set by `RegisterDragDrop`; it needs only an HWND created on the OLE-initialized STA thread. `WS_EX_NOREDIRECTIONBITMAP` only changes how the window's content reaches the compositor (no GDI redirection surface), not hit testing; `WS_EX_NOACTIVATE` and `WS_EX_TOOLWINDOW` do not block drops. The WPF record shows the drop target itself registering fine on a band window (`docs/wpf/ROADMAP.md:460-462`: "WPF's AllowDrop reaches an HWND created by CreateWindowInBand, confirmed by reading the window's OleDropTargetInterface property"); what failed there was integrity, not window style.
- Click-through: a window with `WS_EX_TRANSPARENT` (the OSD) or a layered window with a transparent pixel under the cursor is skipped by `WindowFromPoint`, so it would never see `DragEnter`. The notch window has neither flag; its hit area is the `SetWindowRgn` region (ADR 0004), and a point outside the region falls through to whatever is behind. So a drag is accepted exactly inside the region = drawn shape + 3 px. A drag released in the 3 px halo counts as a drop on the island (same trade as clicks, ADR 0004).
- The region is updated every painted frame on the UI thread (`apply_latest`). The UI thread is BLOCKED in OLE's modal loop only during Plith's own drag-out; during a drag-in the UI thread is the one receiving DragEnter/DragOver (OLE calls the target in the target's apartment through the message loop), so region updates continue and the target can grow with the island (this is also what makes a drag-hover open of the island visible to the target).
- Thread: OLE requires `OleInitialize` (STA) on the thread that registers; `process.rs:25-27` already does it, `CoInitializeEx(MTA)` elsewhere is on other threads only. Rule: no thread that later needs OLE may have called `CoInitializeEx(MTA)` first (would give `RPC_E_CHANGED_MODE`). The UI thread must also keep pumping messages (it does) or foreign drags freeze.

### What the notch must do so a drag over the collapsed pill opens it
- Mouse input does not arrive during a foreign drag: OLE's loop owns the mouse, so there are no `WM_MOUSEMOVE`/`WM_LBUTTONUP`/`WM_MOUSELEAVE` from the shell (`mouse.rs` events `Enter/Move/Click/Release/Leave` all stay silent). The only signal is `IDropTarget::DragEnter/DragOver/DragLeave/Drop` on the registered window. ADR 0011 says "there is no hover-to-expand", so this needs a new ADR: drag-hover is the one exception (Oyenza does the same, with a 380 ms grace).
- Design: IDropTarget impl emits `ShellEvent::DragHover{x,y}` / `DragLeave` / `Drop{paths}` (screen px converted to island DIP with the same conversion as `message_point`), the app opens the shelf page on DragEnter (after a short dwell, to avoid opening for a drag that merely crosses the pill), keeps the island open while hovering, and starts the normal 400 ms leave collapse on DragLeave/Drop. While a drag is hovering the app must NOT treat a missing `Leave` as the pointer being out (the `inner.tracking` flag in `mouse.rs:146-152` can be stale: after a drag the first `WM_MOUSEMOVE` will not emit `Enter` if `tracking` stayed true, and a `WM_MOUSELEAVE` during OLE capture may have been swallowed; reset `tracking` and the press state in DragLeave/Drop).
- The accept test must happen in DragEnter (QueryGetData for CF_HDROP and the other accepted formats); return `DROPEFFECT_NONE` for everything else so the circle-slash cursor is honest. Effects: Copy by default, Link with Alt, never Move (WPF and Oyenza agree; we store references).
- The pill region is only 200 x 32 DIP (+3 px). That small target is the chance for a "missed drag" complaint (WPF fought the same issue: `docs/wpf/ROADMAP.md:488-490` "The approach band is 356x48 DIP, not 190x28 ... the file had to be pressed against the top edge of the screen"). Consider a larger transparent approach band only if measured necessary, but note that any window area counts as hit: a band bigger than the region cannot be a click-through region while also being a drop target; the repo has one window and one region (ADR 0004). Decide with a measurement, not a guess.
- Drop target inside the open page: the whole island region is one target; DragOver gets the point so it can highlight the dashed slot (hot state) and tell the page which wagon/slot is under the cursor. The target helper (`IDropTargetHelper`) draws the drag image over the foreign cursor; with a per-frame DirectComposition swap chain there is no GDI redirection surface under it, and `IDropTargetHelper::Show(false)` may be needed if the drag image paints over the island. Unverified.

### Drag out inside the Rust app
- Starting: today a press calls `SetCapture` (mouse.rs:123-128) and `ShellEvent::Drag` fires after the slop (`mouse.rs:158-163`). For a wagon press the app must `ReleaseCapture()` before `DoDragDrop` (OLE takes its own capture) then call `DoDragDrop` from the UI thread, from the event handler that is processing a real mouse event while `GetKeyState(VK_LBUTTON)` is down (the WPF finding: no live press = hang or `None`; copy its guards: re-entrancy flag, live-button check, never from a timer or pipe message).
- Inside `DoDragDrop`'s modal loop the thread keeps dispatching other messages (WPF note `src/Plith.DropCatcher/DragSourceProbe.cs:119`: "DoDragDrop pumps messages while it blocks, so this timer keeps ticking inside it"), so WM_TIMER (collapse timer), `WM_APP` wakes and the SetWindowRgn updates from the render thread continue. Therefore: set a `dragging_out` flag that suppresses the 400 ms leave collapse and the user-busy suppression during the drag, and clear it (re-evaluate the pointer position) after `DoDragDrop` returns. Oyenza uses `DRAGGING_OUT` the same way.
- The island must not refuse its own drag: while `dragging_out`, our own IDropTarget gets DragEnter for our own data object; accept Move/None quietly (do not re-add the file to the shelf; either check a process-local flag or compare the HDROP paths).
- Must not block the render thread: the render thread is separate (spec `:75`), so motion continues; the cost is that UI-thread-only work (hit region updates for the shape!) is also pumped inside the modal loop, so it continues too.
- Dead entries: before drag-out, stat each path and skip what vanished (Oyenza: "Files moved or deleted are skipped"); after `DoDragDrop` returns with Move... we only offer Copy|Link so no removal is needed; the wagon stays.

### Thumbnails / drag image
- `IShellItemImageFactory::GetImage` with `SIIGBF_THUMBNAILONLY | SIIGBF_BIGGERSIZEOK` (as WPF), or `SIIGBF_ICONONLY` for non-previewable types; per-path cache; run on worker threads with `CoInitializeEx(MTA)`; hand the HBITMAP (premultiplied BGRA) to the render thread, which uploads to a D2D bitmap. The mock's wagon has NO thumbnail (type tag + two-line name); the type tag is derived from the extension in `plith-core` (pure). Thumbnails are therefore optional for R5. If wanted, the drag image from the shell data object comes free with `IDragSourceHelper2::InitializeFromWindow`/shell's own drag-image support, so a custom bitmap is only needed for multi-select count chips.

## 4. Integrity (UIPI)
- `plith.exe` is medium (ADR 0002). A drag from an ELEVATED source (admin Explorer, admin terminal, an app run as administrator) into a medium target is blocked by the OLE/UIPI rule. Measured in this repo, the symmetric cases: `docs/wpf/ROADMAP.md:456-465` "Explorer runs at Medium, and UAC blocks the cross-integrity COM call that DoDragDrop makes. Not one DragEnter was delivered." (medium source, high target) and the table at `docs/wpf/ROADMAP.md` (HIGH source -> Explorer: `DoDragDrop` returns `None`, "UIPI blocks both directions"). I did not find a measurement of an elevated source over a medium Rust target, but the second row is exactly that pair (high source, medium target), so the same result is expected.
- What the user sees: the cursor shows the "no drop" circle-slash over the notch; `DragEnter` never reaches Plith (no log line, no hover open), the shelf stays closed. There is no error message anywhere. Things to design: (1) accept the limitation and say it in docs/settings (Oyenza has the same limit; `docs/decisions/0002-integrity-split.md:15-17`); (2) optional hint: the polling route still works because `GetCursorPos`/`GetAsyncKeyState` are state reads, not messages (`docs/wpf/ROADMAP.md:474-478`), so the notch could detect "left button down, cursor over the pill, no DragEnter within N ms" and show a one-line hint "Yönetici penceresinden sürükleme desteklenmez". Measure before building; guess-free alternative is documentation only.
- Reverse: a drag out of Plith onto an elevated window (e.g. admin Explorer) is also blocked; same no-drop cursor, `DoDragDrop` returns `DRAGDROP_S_CANCEL` or `DROPEFFECT_NONE`.
- Standard (non-admin) user and an elevated notch: `docs/STATUS.md` says "An elevated notch fails closed too" (a notch started elevated would then be a HIGH target and block normal Explorer drags: the same defect as WPF). Verify `plith.exe` is never started elevated by the installer or autostart, since that would silently recreate the WPF problem.
- Secondary: foreground fullscreen games. Borderless games still accept the island; exclusive fullscreen hides the notch (spec `:77-79`), so no shelf there, by design.

## 5. Risks and what to measure

Risks (ordered):
1. UI thread blocked by OLE: inside our own `DoDragDrop` the app code still runs (messages pump), but a foreign IDataObject GetData on a slow provider (network, browser stream) blocks the UI thread and thus input and region updates. Large FileContents streams need a worker.
2. Hover-open feel: DragEnter on a 200 x 32 target is a small, hard-to-hit area; the dwell time and the leave grace (Oyenza 380 ms) define whether it feels "wrong" like the WPF shelf. Needs a console feel test with Berke, not a scripted test.
3. Stale mouse state after drags: `tracking`, `press`, capture and `last_point` in `mouse.rs` may be inconsistent after OLE swallowed `WM_MOUSELEAVE`/`WM_LBUTTONUP`; collapse timer must not fire mid-drag, and must fire after.
4. Page-turn and shape animations while a drag hovers: the page must not turn under a held file; and the hit region changes every frame (apply.rs) while OLE hit-tests; flicker of target under a stationary cursor would show as DragLeave/DragEnter chatter. Debounce on the app side.
5. Press lost on re-render: the WPF instrument failure (§4 status). In Rust the display list is rebuilt per frame, so keep pressed item id and press origin in app state, not in tile identity; a store `Changed` between press and slop must not cancel it.
6. Persistence format: shelf.txt in `%LOCALAPPDATA%\Plith` (matches `plays.txt`, `crates/plith/src/plays_file.rs`). Text, URL and image drags need a payload folder; garbage-collect it on remove/clear/cap (never `rm` a variable path from scripts; do it in Rust with a literal-path-built, validated child of the shelf folder).
7. Capacity and layout: the mock fits 4 wagons + the dashed slot in 560 px; the WPF cap is 10 (grid). Decide: horizontal scroll on the siding, or two rows at a taller page, or a cap of 4 to 5. A cap beyond what is drawn recreates the WPF bug (files on the shelf, off the screen).
8. Elevation / UIPI as above; document, optional hint.
9. Drag-image over a DirectComposition window (IDropTargetHelper) and cursor-feedback: unverified.
10. COM apartment: do not add `CoInitializeEx(MTA)` on the UI thread; thumbnails on workers only.
11. Exceptions across COM: wrap every IDropTarget/IDropSource body in `catch_unwind`; on panic return `E_FAIL` and flag the app like `on_panic`.

What to measure (console session only; no scripted mouse):
- `RegisterDragDrop` return value and whether DragEnter arrives at all on the live notch window, at rest and open; log line with the screen point, DPI-converted island DIP, format list, effect returned (a `drag` line in `plith.log`, same style as `motion`).
- Hover open: time from DragEnter to the page being on screen; whether `Leave`/collapse fires during the drag; DragEnter/DragLeave chatter count while the island morphs.
- Motion during drag: the existing `motion` line (frames, fps, hitches, worst gap) for open-on-drag, close-after-drop, and while holding a drag over the island; bar is 0 to 1 hitches at 240 Hz.
- UI thread cost per DragOver and per Drop (CF_HDROP of 1, 10 and 1000 files), and a slow-provider case (browser image, OneDrive placeholder).
- Drag out: `DoDragDrop` return and effect to Explorer, to a browser upload field, to chat (Discord), to a text editor; multi-select; Esc cancel; release over empty desktop; the wagon stays; app survives; pointer state after return.
- Integrity: an elevated Explorer/terminal drag into the pill (expect no DragEnter) and out to an elevated window; capture the cursor the user sees and `integrity` in the log. Confirm `plith.exe` runs at Medium (WPF logged "Started. Integrity: <level>").
- Browser sources: Chrome/Edge image drag, link drag, text drag, Outlook attachment, 7-Zip/Explorer-in-zip drag: list formats on the data object (a debug helper that logs `EnumFormatEtc`) before deciding what to accept.
- Idle: with the shelf registered and no drag, zero wakeups added (G2); `RegisterDragDrop` adds no timers. Check the idle check still passes.
- Persistence: restart with a deleted file on the shelf; cap behavior; 0-byte and folder items.

## Decisions needed from Berke (these shape the design, not facts)
1. Accept only files (CF_HDROP, like WPF and Oyenza) for R5, or also text/URL/image drags from browsers (needs a payload folder and breaks references-only)?
2. Capacity and layout for the 620 x 214 page: 4 wagons + slot (mock), scroll, or two rows? (WPF cap 10.)
3. Hover-open on drag: dwell time and grace (Oyenza: 380 ms grace), and a one-paragraph ADR amending 0011.
4. Hint for elevated sources, or document only.
5. Shelf.txt as the store (Notepad-editable, matches WPF) so existing users keep their shelf on migration? WPF path is the same `%LOCALAPPDATA%\Plith\shelf.txt`: the Rust app can read an existing file as is.
